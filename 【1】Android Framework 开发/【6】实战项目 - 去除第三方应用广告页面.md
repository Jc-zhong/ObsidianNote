## 场景：

点击一个应用时，会弹出广告页面，读秒结束或主动点击跳过后，才进入到 **MainActivity**

## 1、分析需求

常用命令 - 查看 **top Activity** 具体是什么
```shell
adb shell dumpsys activity activities
# ResumeActiviry: ActivityRecord{91b87aa u0 com.example.myapplication/.MainActivity t78}

# 这里的 ResumeActivity 就是当前 top 的 Activity
```


## 2、方案选择

### 2.1 A方案：启动 Activity时 过滤 广告Activity ，直接跳转至 MainActivity

`dumpsys` 发现广告页面和主页面不是同一个 **Activity** ，广告页面是第一个启动页面，然后回跳转到 主页面
故以此得到相应的解决方案：
**按照以前的分析思路：**  

              **应用层 APP   --->   应用框架层 Framework  --->  system_server 顺序来**

应用层：即启动广告页面的是 **Launcher** 这个应用，故考虑是否可以在 **Launcher** 中修改？

这样修改可能会出现的情况：
`A. 启动应用不一定在框架，在其他应用商店也是可以的`
`B.Launcher 也有可能是安装第三方的`

应用框架层修改：基本可以覆盖所有情况
优点：简单快捷，可以较快实现功能
缺点：有可能破坏一些应用的初始化时许，故可能该方案不能覆盖针对所有带广告的应用

### 2.2 B方案：在广告 Activity 模拟一个触摸点击跳过的动作触摸事件

发现广告页面一般会有一个跳过按钮，是否可以考虑在广告 **Activity** 模拟一个触摸点击跳过的动作？

优点：最大限度保证带广告应用的自身逻辑，不会破坏应用的初始化时许
缺点：还是能够看到短暂广告，而且不是每个应用都有跳过按钮，并且跳过按钮的位置也有可能不一致，导致无法覆盖所有应用，需要挨个适配

### 3.2 B方案的实现：在广告 Activity 模拟一个触摸点击跳过的动作触摸事件

要模拟一个触摸事件 `onClick` ，就要知道 `onClick` 是怎么触发的

如图：需要在 **View** 中的 `onTouchEvent` 中先触发 `ACTION_DOWN` 事件 -> 短暂时间后 -> 再触发 `ACTION_UP` 事件，最后才能触发 `onClick` 事件

![[06-exp-01.png]]

那么 `onTouchEvent` 又是由谁触发的呢？我们添加 日志输出栈方法 看看

![[06-onTouchEvent.png|300x100]]

日志分析：

可以看到 **SpalashActivity** 的 `onTouchEvent` 事件是由 **Activity** 的 `dispatchTouchEvent` 事件调用过来的

**这里就可以得出：我们可以通过修改框架层 Framework 的 Activity dispatchTouchEvent 方法，以此来影响 SpalashActivity 的 onTouchEvent 事件。**

**（虽然其他更深一层的类也可以实现，但要遵循最小修改原则，因此只修改与 SpalashActivity 最亲近的类 Activity ，以降低修改代码带来的风险。）**
